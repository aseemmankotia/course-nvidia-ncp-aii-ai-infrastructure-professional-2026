## Chapter 9: Slurm Scheduling and Training-vs-Inference Resource Planning — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Slurm command to submit a non-interactive batch job script? | sbatch script.sh — Exam tip: sbatch queues the job asynchronously; srun runs interactively/blocking; salloc reserves resources for an interactive shell. |
| 2 | Which Slurm flag requests generic resources like GPUs, e.g., 8 GPUs? | --gres=gpu:8 — Exam tip: gres (generic resource) is how Slurm tracks non-CPU resources like GPUs; must be defined in slurm.conf/gres.conf first. |
| 3 | Slurm flag to guarantee a job doesn't share a node with other jobs? | --exclusive — Exam tip: used for large training jobs needing full node bandwidth/memory, preventing noisy-neighbor interference. |
| 4 | Slurm vs Kubernetes: which is preferred for tightly-coupled MPI training with gang scheduling? | Slurm. Exam tip: Kubernetes' default scheduler doesn't natively gang-schedule; Slurm does all-or-nothing allocation for synchronized job start. |
| 5 | Slurm vs Kubernetes: which is preferred for autoscaled, latency-sensitive inference serving? | Kubernetes (with HPA/KEDA + Triton/KServe). Exam tip: Kubernetes handles rolling updates, self-healing, and elastic scale-out/in that inference workloads need. |
| 6 | What Slurm construct lets admins define different scheduling policies (walltime, priority, preemption) for different workload types on the same cluster? | Partitions (with associated QOS). Exam tip: e.g., a 'train' partition with long walltime/low priority vs an 'infer' partition with short walltime/high priority. |
| 7 | What is Slinky (SchedMD/NVIDIA project)? | A hybrid project that runs Slurm workloads as Kubernetes-managed resources, enabling shared node pools between Slurm (training/HPC) and Kubernetes (inference/services). Exam tip: it's the key answer for 'coexistence of Slurm and Kubernetes on shared infrastructure' questions. |
| 8 | Why is inference GPU memory footprint typically smaller than training? | Training stores activations, gradients, and optimizer states across the full model; inference only needs weights + activations for a forward pass. Exam tip: this is why MIG/time-slicing works well for inference density but not for large training runs. |
| 9 | Which Kubernetes autoscaling mechanism scales pods based on custom metrics like request rate or queue depth (not just CPU)? | KEDA (Kubernetes Event-Driven Autoscaling). Exam tip: HPA alone typically scales on CPU/memory; KEDA extends scaling triggers to external metrics relevant to inference traffic. |
| 10 | What does MIG stand for, and what's its exam-relevant use case? | Multi-Instance GPU — partitions a single GPU (e.g., A100/H100) into up to 7 isolated instances. Exam tip: used to increase inference density/utilization; NOT typically used for large distributed training jobs needing full GPU memory/bandwidth. |
| 11 | Slurm command to view current job queue status? | squeue — Exam tip: sinfo shows partition/node status; scontrol show job <id> gives detailed job info; squeue shows pending/running jobs. |
| 12 | Key decision criterion: Slurm vs Kubernetes for a mixed AI workload cluster? | Choose based on job pattern: batch, synchronized, fixed-duration, HPC-style jobs → Slurm. Long-running, independently scalable, service-style, event-driven workloads → Kubernetes. Exam tip: this exact criterion pair is heavily tested. |
